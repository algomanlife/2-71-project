# CUDA Lab Baseline Audit — Measurement Validity

Task-1 audit of `research/cuda-lab/` (2026-11-05, code at this branch).
Question: are the lab's reported performance numbers accurate,
reproducible, and representative of actual GPU computation? Each answer
cites the code; gaps are listed with status.

## Q1 — Is GPU execution synchronized correctly? [VERIFIED]

- Timing uses CUDA events recorded on the default stream around the
  measured launch, `cudaEventSynchronize` on the stop event
  (`src/kernels.cu`, `run_bench`); `cudaGetLastError` checked after
  every launch; warmup ends with `cudaDeviceSynchronize`.
- Bench kernels are launched on the default (null) stream — events and
  kernels are stream-ordered, so the measurement brackets exactly the
  kernel's GPU execution.

## Q2 — Do measurements include initialization, transfers, compilation? [VERIFIED — excluded]

- All allocations/memsets (`d_sink`, EC buffers) happen **before**
  `cudaEventRecord(t0)` (fixed in the Phase-2 work; EC case explicitly
  restructured).
- Host→device copies: the benches need no per-run H2D (operands are
  device constants / generated in-kernel); the global-rw buffer is
  initialized before timing.
- Compilation/JIT: the binary is compiled ahead of time; the warmup
  launch absorbs first-launch overhead (module load, L2 warm).
- `launch-latency` intentionally measures the launch pipeline itself —
  its semantics (submission+execution of empty kernels, back-to-back)
  are documented in the README op table.

## Q3 — Are reported operation counts independently verifiable? [VERIFIED]

- `ops = blocks × threads × iters` (per bench: EC = threads,
  launch-latency = iters) — arithmetic by construction.
- The Phase-3 validity gate (`--verify/--verify-only`) proves the
  iterations execute: per-thread final values are cross-checked
  bit-for-bit against host references; DCE/loop-elision would diverge.
- The experiment runner refuses to time any bench that fails
  verification, and records carry `verified: true`.

## Q4 — Do warm-up, clock variation, and thermal effects influence results? [GAP — documented]

- Warmup exists but is minimal: ONE launch of 16 iterations before
  timing. GPU boost-clock ramp-up and L1/L2/instruction-cache warm-in
  typically need longer; the 5-repetition median in the runner mitigates
  but does not eliminate cold-start bias (rep 1 can be slower).
- No clock/power telemetry is captured by the lab runner (the app-level
  sweep has `nvidia-smi dmon` sampling; the lab does not).
- **Mitigation implemented in this PR:** `--warmup N` option (default
  16 = baseline behavior preserved); methodology below recommends
  `--warmup 1000` for steady-state measurements.
- Clock locking (`nvidia-smi -lgc`) and thermal warm-up procedures are
  documented as rig-side requirements for publishable numbers.

## Q5 — Are there appropriate correctness checks? [VERIFIED]

- ctest `public_vectors`: modmul chains vs public vectors (A·B, A·B⁸,
  A·B⁶⁴), affine EC scalar-mul vs public points (2G/3G/7G/k·G) —
  generated by the independent python `ecdsa` library.
- Phase-3 verification gate (see Q3) — runs per bench before timing.

## Q6 — Are results reproducible across repeated runs? [VERIFIED with caveat]

- The runner performs N repetitions and reports median/min/max/stdev
  with a 2×-pooled-stdev noise guard for comparisons.
- The user's 5-rep hardware runs (int32-mix 12,654.669 Gops/s etc.)
  demonstrate the workflow end-to-end; variance values are recorded in
  the results files.
- Caveat: single-invocation `--reps` inside the binary reports one
  event-timed measurement; only the runner's per-repetition invocations
  provide true repetition statistics (documented in the README).

## Metric separation [VERIFIED]

Synthetic Gops/s, memory GB/s, EC ops/s, and the application's
key-search Mkeys/s are defined per bench and never mixed (lab README
rules; `OPTIMIZATION_RESULTS.md` rules; the application's benchmark
docs). The historical application log (2^37-key range, 7,485.9
Mkeys/s early-termination) is stored verbatim and analyzed separately
(`TRAVERSAL_ORDER_ANALYSIS.md`).
